### 1-3 `台帳`
| 列 | 型 | 備考 |
|---|---|---|
| ID | 文字 | |
| 日付 | 日付 | |
| 内容 | 文字 | 例：ROOKIES 昼ごはん |
| 種別 | receipt／car／fee／settle／other | |
| 合計 | 数値 | 明細の合計 |
| 支払者 | Airi／Miha／Rinka | 財布から出た人 |
| 大会ID | 文字 | 任意 |
| 明細JSON | JSON | `[{"label":"オムライス","amount":1190,"targets":["Airi"]}]`。carは ガソリン／高速／駐車場 の3行、targets＝乗車メンバー |
| 負担JSON | JSON | `{"Airi":1380,"Miha":0,"Rinka":2870}` 保存時に計算して持つ（表示を速くする） |
| 車JSON | JSON | carのみ：`{"行き先ID","運転者","往復":true,"距離":72,"燃費":9,"単価":162,"駐車場":1400}` |
| メモ | 文字 | |
| 作成日時 | 日時 | |

精算（settle）：支払者＝払った人、明細1行 targets＝受け取った人。式は他の行と同じ（払った人の「支払」が増え、受け取った人の「負担」が増える）ので、残高が自然に相殺される。
残高：人ごとに 支払合計−負担合計＝ネット。ネット＋が受け取る側。送金の組み合わせは現行`calcProjectSettlement`の貪欲法を流用。10円丸め。

## 2. 既存データの変換（移行スクリプト `migrateV2()`）

### 2-1 大会（21件）
- 列を1-1へ写す。資料1〜5→資料JSON。ラウンド空→単発。
- 旧「ステータス」列は無視。

### 2-2 やること（大会ごとに生成）
| 旧列 | 生成するやること |
|---|---|
| エントリー_状況／エントリー_期限 | entry「エントリー」期限＝エントリー_期限、済＝状況が提出済 |
| 音源_要否＝事前 | music「音源 事前提出」期限＝音源_期限、済＝状況が提出済 |
| 音源_要否＝当日CD | backup_cd「音源CD 持参」当日。**済は開催日を過ぎたらtrue扱い**（旧データの「準備中」残りを解消） |
| 音源_当日CD＝true かつ 要否＝事前 | backup_cd「予備CD 持参」当日 |
| 動画_要否／写真_要否 が不要・空以外 | other「動画」「写真」期限＝各期限、済＝状況が提出済 |
| エントリー費_金額>0 | entry_fee「エントリー費」単価＝金額、数量＝3。支払方法＝当日→当日、それ以外→期限＝エントリー費_期限、済＝振込済 |
| 観覧費_支払方法＝事前支払い／当日支払い かつ 大人単価>0 | view_fee「観覧費」単価＝大人単価、数量＝各家族の大人数合計（無ければ3）、当日／期限＝観覧費_期限、済＝振込済 |
| 衣装_メモ | 空のため生成しない |

### 2-3 台帳
- **おでかけ記録16件を全件移行**：`calcTripCost`で計算した ガソリン／高速／駐車場 を car明細（targets＝乗車メンバー）、その他費用JSONをそのまま明細に。支払者・日付・目的→内容。目的地→行き先マスタ照合。
- **回収ステータス**（プロジェクトごとの `{"Miha":true,"Airi":true}`）→ settle行を生成（日付＝プロジェクト完了日、金額＝そのプロジェクト内のネット送金額）。
- **大会側の金額**：エントリー費_振込済＝true の大会は fee行（支払者Rinka、targets＝3人、合計＝金額×3）を生成し、`家族_エントリー費_支払済`＝true の家族分は settle行を生成。観覧費も同様。
- **検証**：移行後に全員のネットを計算し、9/1時点の実態（全額精算済み＝ネット0）と一致するか確認。ずれた行はメモに「移行要確認」を付けて一覧を出す。**一致しない場合は大会側の金額履歴は移行せず、おでかけ記録のみ移行する**（藤本さんに選んでもらう）。

### 2-4 マスタ
- 行き先：記録の目的地ごとに最新の 距離／高速料金 から生成（EBISU WORKS nagoya 39km 1410/1040、サンマンション高畑 37km 1080/1080、オアシス21 36km 1080/1080、中村公園 40km 1040/1040、ウィル愛知 39km 0/0）。
- 車：6行→3行に重複排除（Airi 8／Miha 8／Rinka 9）。
- 設定：ガソリン単価＝最新記録の166。

### 2-5 実行手順
1. `migrateV2(dryRun=true)`：新シートに書かずログだけ出す。件数と残高検証を確認
2. バックアップ（既存`backupContestSheet`を拡張して全シート複製）
3. `migrateV2(dryRun=false)`：新シート作成・書き込み
4. 旧シートはそのまま残す（旧アプリは切替まで動き続ける）

## 3. 実装計画

### 3-1 構成
| 層 | 決め |
|---|---|
| 配信 | GitHub Pages。大人用＝`ramuse-lock/ramuse-contest`、子供用＝`ramuse-lock/ramuse-kid`。**ソースは大人用リポジトリ1本**、ビルドで2つの出力（`mode=adult`／`mode=kid`）を作り、子供用リポジトリへは成果物だけをpush |
| フロント | Vite＋Preact＋TypeScript（軽量・ビルド1回・PWA）。CSSは素のCSS変数（モックのトークンをそのまま移植）。アイコンはMaterial Symbols Rounded |
| バックエンド | 現行`Code.gs`を継続（Sheets＋Calendar）。`serveApi`にv2エンドポイントを追加。読みはJSON/JSONP、書きは現行`serveRpc`方式（args64）を踏襲 |
| 起動の速さ | 前回取得データをlocalStorageに保存→起動時に即描画→裏で最新取得→差分があれば静かに更新。タブ切替は取得なし。保存は先に画面へ反映し裏で送信（失敗時は戻してトースト） |
| カレンダー | 現行`getCalendarEvents`を月単位で取得しキャッシュ。Google色→系統色の変換はフロント |
| 子供モード | APIに`mode=kid`。サーバー側で 台帳・お金のやること・編集系を返さない。下タブ3つ |
| 認可 | 現状は**URLを知れば誰でも書ける**。大人用はPIN（設定シート）を初回入力→localStorage保存→書き込みAPIに付与。子供用は読みのみ |
| 旧GAS版 | 切替後もURLは残す（戻せる状態）。落ち着いたら停止 |
